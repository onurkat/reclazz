SAP Commerce / Hybris

SAP Commerce: your daily edit loop

Set up once, find your edit and verify the running server.

Start with one working reload

Attach Reclazz once, compile a small Java edit and check the changed result in the running server.

  1. Follow the IntelliJ + SAP setup.
  2. Start the server with the agent and wait for watching to begin.
  3. Compile your edit, repeat the same operation and check its actual result.

Your changes and their conditions
Your changeResultBefore you try it
Save *-items.xml / *-beans.xml Reloads, with a condition

Platform generation and builds can reload the generated classes. Persistence, type-system updates and native reflection are separate requirements.

Next: Check generated bytecode. Apply the platform schema update when required.

Create columns through Update Running System Reloads, with a condition

Manual HAC action is separate from reload. autoUpdateRunningSystem=true is a distinct off-by-default dev-only DDL opt-in.

Next: Choose the schema action explicitly and verify the type/persistence result.

Apply changed SAP configuration keys Reloads, with a condition

Changed keys reach the native Config path and acknowledge independently when successful. A startup-only consumer still needs a restart.

Next: Check each key’s runtime consumer and pending status.

Edit type/enum localization or Backoffice labels Reloads, with a condition

Recognized physical locale/label files refresh the platform caches they serve. Broader tenant/cluster acceptance is not implied.

Next: Check a new lookup or reopen the affected Backoffice view.

Import a changed ImpEx file automatically Reloads, with a condition

autoImpex=true opt-in writes live development data. REMOVE/macro-expanded REMOVE is refused unless separately permitted; no rollback.

Next: Use disposable data; inspect import results and guard diagnostics.

Refresh supported interceptor mappings Reloads, with a condition

Mappings and native registry identities survive interceptor bean refresh. Watched XML additions and setter-defined interceptor ref/typeCode edits reconcile each owner’s context and ModelService registries. Mapping definitions requiring recreation, and unsupported removal, need a restart.

Next: Check the registry result and a relevant live model operation.

Edit OCC field sets, mappings or supported directives Reloads, with a condition

Dedicated field-set/request-mapping/populator/list-merge paths have individual ownership and registration limits. Not arbitrary platform topology reload.

Next: Read the matching path and verify the actual OCC response.

Edit *-backoffice-config.xml Reloads

Runs the native F4 cockpit-config reset in the owning tenant/session, rebuilding persisted configuration from module sources. This also resets configuration changed in the UI; widgets are not reset. Disable with backofficeConfigReset=false.

Next: Open a new view; disabled or failed resets report WARN instead of success.

Add a Backoffice @SocketEvent action Reloads, with a condition

Requires an agent-prepared class; standard modules follow the backoffice-module admission conditions. Generic reflection lets newly composed default MVC components bind public non-static handlers with at most one parameter. One-parameter native detached dispatch measured on JDK17/21; local Chrome acceptance on 2211-jdk21.8/JDK21 verified a new view binding, retained open-view binding, body edit and removal without stale dispatch. Open components retain bindings.

Next: Compose a new view. Invalid native signatures keep PENDING; static reload is unverified and keeps PENDING. Removed added methods stop stale dispatch.

Reload a Java Backoffice module Reloads, with a condition

Explicit backoffice-module=true metadata, selected extension and exact WidgetClassLoader; one owning backoffice/classes file with identical initial bytes. Source compilation and IDE output saves are tested with a synthetic opaque loader; preparation and added-method reload measured with both native SDK loaders.

Next: Start with the agent before the class loads. Rebuild stale output/JAR bytes and restart if initial admission fails. Duplicate definitions remain unprepared; reload targets only the prepared owner. Local Chrome acceptance on 2211-jdk21.8/JDK21 verified startup preparation and source-to-widget handler add/edit/removal; broader widget routing remains unverified.

Edit an observed process XML or add a new process XML/resource bean Reloads, with a condition

With the SAP automation module, a new name can be published into a warm standard native cache only from an exact resource singleton added by a watched, observed Spring source. Both save orders are supported. Unproven siblings, duplicate/existing names, dynamic definitions and replaced owners are refused. Each proven native owner is evaluated in its own tenant/session scope; failures and proof retirement stay local to that owner. Cold caches retain native lazy loading. Proven later edits preserve historical versions; deletion requires restart.

Next: Verify a newly started process. Already started processes keep their version within this JVM; no migration, replay, cache-eviction retention or cluster propagation.

Refresh stored documents after an indexing provider/resolver reload Reloads, with a condition

autoSolrReindex=true, SAP module, exact provider metadata, stock local standalone provider/strategy, explicit stored PKs and 10,000-document limit. Property providers use partial updates; type resolvers use whole-document UPDATE. Normal native listeners and operation bookkeeping still run.

Next: Verify the stored search field separately from the class reload receipt. Unknown targets, missing cores, remote/cluster mode and incomplete reads are refused.

Add an extension to the platform Needs a restart

The extension list is established at startup. Generated-bytecode reload does not enroll a new extension.

Next: Build the platform and restart.
