Verify data separately from Java

A changed class, ORM mapping, database schema and cached result are separate things to check. Start with the exact edit below.

Entities, repositories and caches

Your changes and their conditions
Your changeResultBefore you try it
Add a mapped field to an existing entity Reloads, with a condition

Requires enhanced visibility plus supported jpaRefresh=true/DDL-enabled mapping path; stock companion fields are not native ORM members.

Next: Prepare schema/mapping prerequisites or restart.

Add a new JPA entity with a prepared schema Reloads, with a condition

jpaRefresh=true, explicit Hibernate validate, one unit and standard provider/factory in the recorded graph. No automatic migration or update-mode switch.

Next: Prepare table/columns, compile and verify native mapping installation.

Retry a new-entity mapping after a schema failure Reloads, with a condition

Failed candidate leaves the previous factory open before install. Identical bytes are ignored; changing pending mapping declarations is refused.

Next: Fix schema, then compile a body-only edit to the same pending entity.

Keep old persistence contexts/transactions through a rebuild Needs a restart

A successful persistence-unit swap retires the old native factory. Holding active old contexts across it is unsupported.

Next: Finish database work first; restart/recover unsupported retained contexts.

Edit supported Spring Data query methods Reloads, with a condition

Warm singleton Repository products and bounded direct holder repair. Scalar H2 native-query evidence does not cover new interface methods/all query shapes.

Next: Check the query result and the retained managed consumer.

Invalidate caches dependent on changed helper code Reloads, with a condition

Observed synchronous Spring cache dependencies in stock companion mode; region-level conservative eviction. Async/unwatched/pre-attach work is not complete.

Next: Exercise the cache first, reload and check next-call freshness.

Rebuild a custom cache owner after helper changes Reloads, with a condition

refreshOwnersOnHelper opt-in for supported singleton owners. Non-singletons, FactoryBeans and event-listener owners are declined.

Next: Name the eligible owner and check lifecycle/state reset.

Restart needed when

If your mapping or cache-owner shape is outside the listed conditions, follow its next action. A Java reload does not migrate a database.
