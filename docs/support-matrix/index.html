Scope notes (5)

These expectations describe limits, rather than an edit you can make. The filters include them.

Assume every Java 17+ vendor/version is certified

Not verified yet

Java 17+ is the target, not certification of every runtime. The main portable records cover stock SapMachine 17/21 on macOS arm64.

Next: Validate your exact runtime and edit shape.

Read conditions

Reevaluate every filtered component after a profile/property edit

Not verified yet

New-component conditions are evaluated at registration. General rediscovery after a profile/property edit and replay of startup imports or auto-configuration are outside this path.

Next: Restart for changed startup topology, or validate the narrower path you use.

Read conditions

Assume every serializer discovers companion members

Not verified yet

The explicit Jackson adapter does not establish support for arbitrary Gson/custom mappers or record creators. On stock JVMs, original-class reflection remains limited.

Next: Validate the serializer or restart when native reflective visibility is required.

Read conditions

Assume XA, hosted clusters, rebalances or exactly-once reload

Not verified yet

Local broker observations do not certify hosted clusters, failure modes, transactional topology, rebalances or exactly-once reload. Rabbit reply/async and broader custom-container paths remain separate gaps.

Next: Validate your broker, lifecycle and delivery policy with targeted acceptance.

Read conditions

Expect arbitrary files to trigger a reload

No change applied

Reclazz recognizes specific suffixes and owned resources. It takes no reload action for an unknown kind. Your framework may independently serve that file.

Next: Check the resource classifier and your application’s resource pipeline.

JavaEdit an existing method body Reloads

Method-body edits reload when compiled into a watched output. Existing object fields stay in place on the JVM-only path. A separate framework refresh can recreate beans.

Next: Compile the edit, repeat the original operation and check the changed result in the same JVM.

Read conditions
JavaAdd or remove a method Reloads, with a condition

Added or removed methods work through hot-compiled callers on a stock JDK. They are not native members of the original Class. A caller using a removed method gets NoSuchMethodError, or the inherited implementation for a removed override, as after restart.

Next: Compile affected watched callers. Use a supported framework adapter when the operation needs reflection.

Read conditions
JavaAdd an instance field Reloads, with a condition

Stock mode stores added fields separately. Isolated initializers run on first read for existing objects; constructor-dependent or entangled initializers retain type defaults with a reason.

Next: Read the initializer diagnostic and verify an existing object.

Read conditions
SpringRefresh an affected singleton bean Reloads, with a condition

Supported singleton paths recreate the affected bean and repair supported references. Mutable state can reset. Arbitrary external holders are not repaired.

Next: Check lifecycle effects and the result served through an existing application reference.

Read conditions
SpringAdd a new component class Reloads, with a condition

New direct or composed component classes use native naming and registration-time conditions. Singleton, prototype and lazy creation are supported. Full startup scanning is not repeated.

Next: Compile the new class and check its registration and condition result.

Read conditions
SpringAdd an @Bean factory method Reloads, with a condition

Supported lite, full and static configuration paths can register added factory methods. Arguments, aliases, selection and direct conditions have a defined allowlist. Existing names, custom scopes and unknown composed conditions remain restricted.

Next: Check the factory allowlist, then verify product identity and lifecycle.

Read conditions
Web & JSONAdd/change a controller endpoint Reloads, with a condition

Supported mapping rescans discover changed endpoints, including added methods on a stock JVM. Receiver, metadata and classloader restrictions still apply.

Next: Compile the controller and send a request to the intended route.

Read conditions
ConfigurationEdit recognized Boot properties Reloads, with a condition

Recognized Boot properties are checked for binding, conversion and validation before live mutation. Invalid or uncheckable input stays pending. Setter or recreation failure can partially apply.

Next: Fix rejected input and save again. Inspect the actual runtime values, including after a partial failure.

Read conditions
ConfigurationChange direct or computed @Value inputs Reloads, with a condition

Direct and supported computed values can update through their field, constructor or factory path. Each consumer has its own checks and recreation rules. Unsupported expression operations hold the candidate.

Next: Check the expression and consumer shape before retrying.

Read conditions
SAP CommerceSave *-items.xml / *-beans.xml Reloads, with a condition

Platform generation and builds can reload the generated classes. Persistence, type-system updates and native reflection are separate requirements.

Next: Check generated bytecode. Apply the platform schema update when required.

Read conditions
SAP CommerceApply changed SAP configuration keys Reloads, with a condition

Changed keys reach the native Config path and acknowledge independently when successful. A startup-only consumer still needs a restart.

Next: Check each key’s runtime consumer and pending status.

Read conditions
SAP CommerceEdit *-backoffice-config.xml Reloads

Runs the native F4 cockpit-config reset in the owning tenant/session, rebuilding persisted configuration from module sources. This also resets configuration changed in the UI; widgets are not reset. Disable with backofficeConfigReset=false.

Next: Open a new view; disabled or failed resets report WARN instead of success.

Read conditions
JavaRead/write an added field from another class Reloads, with a condition

Both owner and caller must be watched/reloaded in the measured direct-access shape. Field-type changes and every inherited/loader variant are not certified.

Next: Compile both sides and check the shared value on an existing object.

Read conditions
JavaAdd a static field with an initializer Reloads, with a condition

Compile-time constants and separable initializers, including bounded forward conditionals/switches, are supported. Other static blocks and current added-field values are preserved.

Next: Check the new value and any extraction refusal reason.

Read conditions
JavaChange an already initialized static field initializer Reloads, with a condition

resetStatics=true at startup; an existing prepared physical field with a changed isolated pure initializer. Frozen first-load definalization is reflection-visible. Added fields keep execute-once behavior.

Next: Check the reset/refusal diagnostic; restart for captured aliases, constants, missing preparation or refused expressions.

Read conditions
JavaChange an inlined compile-time constant Reloads, with a condition

Callers can retain their old literal until recompiled. AutoCompile can rebuild detected watched sources; unwatched consumers remain outside that repair.

Next: Recompile affected callers or use supported AutoCompile.

Read conditions
JavaAppend an enum constant / remove its final constant Reloads, with a condition

Documented on JDK 17–25 with ordinal-preserving edits. Existing application arrays sized from the old enum length do not grow.

Next: Check enum consumers and any fixed-size application arrays.

Read conditions
JavaInsert/reorder enum values or remove a non-tail value Needs a restart

The edit renumbers ordinals; Reclazz refuses it. Restart alone does not migrate persisted ordinal data.

Next: Review persisted ordinals and restart for the type change.

Read conditions
JavaAdd or remove an implemented interface Reloads, with a condition

Requires a compatible enhanced-redefinition JVM such as JBR/DCEVM. Stock JVMs refuse the type change.

Next: Use a supported enhanced runtime or restart.

Read conditions
JavaChange a superclass Needs a restart

The loaded superclass stays unchanged. Eligible bodies may apply; dependent methods stay pinned and unsafe signatures/constructors can refuse the whole save.

Next: Read partial/refused reporting and restart for the hierarchy.

Read conditions
JavaDiscover added members through arbitrary reflection Needs a restart

On stock JVMs the original Class lacks companion members. Explicit framework adapters have separate scope; arbitrary reflective consumers do not.

Next: Restart, or use a compatible enhanced JVM/explicitly supported adapter.

Read conditions
SpringAdd a component with a web/custom scope or scoped proxy Needs a restart

The new-component path refuses these scope shapes. Normal singleton/prototype support does not imply custom scope enrollment.

Next: Restart under the application’s normal configuration.

Read conditions
SpringChange existing injection or lifecycle metadata Reloads, with a condition

Spring metadata caches are refreshed on supported bean paths. Recreation has state and reference limits; it is not an arbitrary graph rewrite.

Next: Check the recreated bean’s injection and lifecycle behavior.

Read conditions
SpringAdd @PostConstruct / @PreDestroy methods Reloads, with a condition

Supported plain singletons use the javax Spring 5 / Jakarta Spring 6 lanes. Each instance keeps its added destroy callback through later edits/removal.

Next: Verify creation/injection/destruction for the affected instance.

Read conditions

Supported public singleton operations use native interceptors; bounded composed metadata is supported. Compile the caller and respect the proxy/advice allowlist.

Next: Verify commit/rollback or cache behavior, not only the method result.

Read conditions
SpringAdd pre/post authorization to a new service operation Reloads, with a condition

Named classic/modern Spring Security graphs support direct and bounded composed policies. Unknown security infrastructure/advice shapes are refused.

Next: Check both allowed and denied calls with the installed security graph.

Read conditions
SpringEdit an @Aspect pointcut Reloads, with a condition

Next: Check an already-injected reference and inspect unsupported targets.

Read conditions
SpringAdd/edit/remove @Scheduled methods Reloads, with a condition

Direct no-argument void callbacks on supported singletons, with documented proxy/transaction/cache/async combinations. Removal cancels the registration.

Next: Check one current schedule and retirement of its predecessor.

Read conditions
SpringAdd/edit/remove @EventListener methods Reloads, with a condition

Direct callbacks with one reference event input and void/single-event return on supported singletons. Filtering/order/conditions and advice have bounded scope.

Next: Publish a test event; check current delivery and no stale registration.

Read conditions
SpringAdd @TransactionalEventListener methods Reloads, with a condition

Direct void methods on supported unproxied singletons; Spring handles phase/fallback/conditions/order. Reload retires queued callbacks from the old added registration.

Next: Check the intended transaction phase and a later edit/removal.

Read conditions

Direct public methods support void, Future and CompletableFuture with native executor/error handling and supported transaction/cache advice.

Next: Check execution, returned completion and exception handling.

Read conditions

Exact supported factories, plain two-node shapes and one measured direct-child context form. Aliases, broader graphs, proxies/factory products and lifecycle-owned shapes are excluded.

Next: Read the ownership contract and verify the retained caller’s value.

Read conditions

Next: Check status/body and handler precedence; fix ambiguous mappings.

Read conditions
Web & JSONAdd @InitBinder / @ModelAttribute methods Reloads, with a condition

Supported plain controller/advice adapters preserve named binding, model rules and native advice order/selectors. Read the exact callback allowlist.

Next: Check a real binding/model request through the current controller.

Read conditions
Web & JSONAdd Jackson getters, setters or DTO fields Reloads, with a condition

Supported Spring-managed mapper adapter; mutable DTOs and saved annotations. Final added fields are not writable; creator/record/builder additions are excluded.

Next: Check JSON input and output against the installed Jackson version.

Read conditions

Read conditions
SAP CommerceAdd a Backoffice @SocketEvent action Reloads, with a condition

Requires an agent-prepared class; standard modules follow the backoffice-module admission conditions. Generic reflection lets newly composed default MVC components bind public non-static handlers with at most one parameter. One-parameter native detached dispatch measured on JDK17/21; local Chrome acceptance on 2211-jdk21.8/JDK21 verified a new view binding, retained open-view binding, body edit and removal without stale dispatch. Open components retain bindings.

Next: Compose a new view. Invalid native signatures keep PENDING; static reload is unverified and keeps PENDING. Removed added methods stop stale dispatch.

Read conditions
SAP CommerceReload a Java Backoffice module Reloads, with a condition

Explicit backoffice-module=true metadata, selected extension and exact WidgetClassLoader; one owning backoffice/classes file with identical initial bytes. Source compilation and IDE output saves are tested with a synthetic opaque loader; preparation and added-method reload measured with both native SDK loaders.

Next: Start with the agent before the class loads. Rebuild stale output/JAR bytes and restart if initial admission fails. Duplicate definitions remain unprepared; reload targets only the prepared owner. Local Chrome acceptance on 2211-jdk21.8/JDK21 verified startup preparation and source-to-widget handler add/edit/removal; broader widget routing remains unverified.

Read conditions
SAP CommerceEdit an observed process XML or add a new process XML/resource bean Reloads, with a condition

With the SAP automation module, a new name can be published into a warm standard native cache only from an exact resource singleton added by a watched, observed Spring source. Both save orders are supported. Unproven siblings, duplicate/existing names, dynamic definitions and replaced owners are refused. Each proven native owner is evaluated in its own tenant/session scope; failures and proof retirement stay local to that owner. Cold caches retain native lazy loading. Proven later edits preserve historical versions; deletion requires restart.

Next: Verify a newly started process. Already started processes keep their version within this JVM; no migration, replay, cache-eviction retention or cluster propagation.
