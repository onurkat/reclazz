# Constructor dependency bookkeeping during direct class refresh

A direct refresh of a plain constructor-injected singleton can reuse Spring's prepared constructor arguments. Native argument replay resolves the objects again, but on the measured Spring 5.3.39 and 6.1.14 paths it does not restore the dependency registration removed by singleton destruction. That can leave the owner alive when a later dependency is destroyed.

The direct `SpringBeanReloader.refreshBean` path now invalidates only that owner's merged definition before destruction and reconstruction. Native constructor resolution discovers the current dependencies again. Old dependency names are never replayed and unrelated merged definitions remain unchanged.

The additional cache repair applies only to a single known root application context, the native DefaultListableBeanFactory on the two measured versions, a live local plain singleton whose standard definition directly constructs its exact class, and one unchanged cached constructor with prepared arguments. It does not apply to suppliers, factory methods/products, proxies, explicit constructor arguments, method overrides, custom definitions/factories, definition-level qualifiers, bean-definition inheritance, parent/child or multiple known contexts. Stable constructor parameter qualifiers still use native selection; changed constructor/parameter annotations reject this cache repair. Unsupported paths keep their existing reload behavior; skipping the repair is not a claim that their bookkeeping or cascade is supported.

This first stage does **not** add helper/property messaging cascade coordination. It does not recreate consumers that native dependency destruction removes, stop their workers, recover added callbacks, or change property/security/XML reconstruction entrypoints. Kafka/JMS/Rabbit consumer cascade remains unverified as a supported capability and the research desired tests remain open for the next separately audited stage.

`ConstructorDependencyContract` runs against both framework graphs. It checks native cached replay, three direct owner refreshes, later native dependency destruction, current constructor values, candidate removal, stable qualifiers, untouched unrelated instances/metadata, preflight guards, and actual constructor annotation edits. The guard tests concern eligibility for the cache repair, not a new general refusal transaction.
